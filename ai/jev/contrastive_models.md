# Contrastive Language Models: Fast Decision-Making with CLM-8B

## 1. Introduction & Overview
Contrastive Language Models (CLMs) represent a novel class of **System One AI architectures** designed for rapid, low-latency, and generalizable decision-making in autonomous agents, tool-calling, computer-use, and gaming environments. Unlike conventional autoregressive language models that generate responses token-by-token, CLMs treat decision-making as a scoring and ranking problem over candidate actions.

Pre-trained on **60M Q&A pairs**, mid-trained on **30M synthetic hard negatives**, and post-trained on **1M agentic trajectories**, CLM-8B achieves state-of-the-art performance as a verifier on agentic coding benchmarks such as **Terminal-Bench 2.1 (87.6%)** and **DeepSWE (81.6%)** while running up to **9× faster** than traditional autoregressive models.

---

## 2. Why the Term "Contrastive"?
The term **contrastive** directly stems from the model's core training objective: **contrastive learning** via the **InfoNCE loss**.

* **Pulling and Pushing:** During training, given a batch of matched state–action pairs, the model maximizes the dot-product similarity between a state (e.g., context, user query) and its ground-truth positive action ("pulling" them together in vector space), while simultaneously minimizing similarity with all other actions in the batch ("pushing" them apart).

* **Bidirectional Optimization:** The InfoNCE loss is optimized in both directions: state-to-action and action-to-state.

* **Hard Negative Refinement:** During mid-training, the model is exposed to **ves**—actions that are semantically plausible but technically incorrect. Thisteaches the projection head to discriminate subtle differences between correct solutions and tricky distractors, elevating top-1 verification accuracy from 52.1% to 69.2%.

## 4. Notes on the Trainable Projection Head
Rather than fine-tuning all 8 billion parameters of the base LLM, CLM introduces a **20M-parameter trainable projection head**:

* **Dual Structure:** The head is composed of two sub-modules: `state_head` and `action_head`.
* **Dimensionality Reduction:** It maps the high-dimensional base outputs ($`h own to normalized 512-dimensional embeddings ($`e \in \mathbb{R}^{512}`$)optimized specifically for dot-product scoring.
* **Lightweight Adaptation:** Fine-tuning on custom tasks (e.g., agentic workflting) only updates these 20M parameters (`train/finetune.py`), making trainingextremely fast, memory-efficient, and easy to run on standard GPUs.

## 5. State Embeddings vs. Candidate (Action) Embeddings

In the context of Contrastive Language Models (CLMs), **state embeddings** and **candidate embeddings** (frequently referred to as **action embeddings**) are the two specialized numerical representations used to make rapid decisions.

### State Embeddings
State embeddings represent the **current context or situation** the model is analyzing.
*   **What they represent:** This typically includes a user's question, environment context, or a problem description.
*   **How they are created:** They are generated by the **state encoder**, which consists of a frozen 8B-parameter LLM backbone (like Qwen3-8B) paired with a specialized **20M-parameter state projection head**.
*   **Role:** These embeddings act as the "query" in the decision-making process, capturing the essential features of the problem that need to be matched with a solution.

### Candidate Embeddings
Candidate embeddings represent the **potential actions or responses** the model can take.
*   **What they represent:** These can be a set of multiple-choice options, a list of potential tools to call, or various "best-of-N" answer trajectories.
*   **How they are created:** They are generated by the **action encoder**, which uses the same frozen LLM backbone but a different **20M-parameter action projection head**.
*   **Role:** These act as the "keys" that are scored against the state embedding. During inference, the model selects the candidate whose embedding has the highest alignment (calculated via dot product) with the state embedding.

### Key Differences and Benefits
*   **Disaggregation:** States and actions are processed by separate heads, meaning their embeddings are **disaggregated**. This allows the model to cache candidate embeddings (like a fixed list of tool names) and reuse them across many different states without re-encoding them, which is a major driver of the model's **9× lower latency**.
*   **Semantic Alignment:** Through contrastive training (InfoNCE loss), the model learns to "pull" the state embedding toward the correct candidate embedding in a shared vector space while "pushing" it away from incorrect ones.

## 6. End-to-End Flow
In the Contrastive Language Model (CLM) framework, answering a user query involhat transforms raw text into specialized vector representations to make rapiddecisions.

### 1. Input: State and Candidates
The process begins when a user provides two pieces of information:
* **The State:** This is the context or the question (e.g., "Customer: my invoice was charged twice!").
* **The Candidates:** These are the potential actions or answers (e.g., a list ng" or "technical," or a set of best-of-N answer trajectories).

### 2. Embedding Generation
The core of the CLM architecture is the **disaggregated encoding** of states and actions. These embeddings are generated through a two-stage process:

* **Frozen Backbone Encoding:** The raw text for both the state and the candidates is sent to a pooling server (typically **vLLM running Qwen3-8B**). This frozen Large Language Model
(LLM) backbone generates high-dimensional base embeddings.
* **Projection Heads:** These base embeddings are then passed through specialized, trainable **20M-parameter projection heads**:
    * The **state head** processes the base embedding of the state text.
    * The **action head** processes the base embedding of each candidate.
* **Normalization and Caching:** The resulting vectors (typically 512-dimensione the backbone and heads are fixed during inference, these embeddings are often**cached**. If a candidate (like a tool name) is reused across different user queries, the system skips the encoding step and pulls the vector directly from memory, contributing to the
model's **9× lower latency**.

### 3. Scoring and Comparison
Once the embeddings are in the same specialized vector space, the model performs a **similarity check**:
* **Dot Product:** The system computes the dot product between the single **stavailable **candidate embedding**.
* **Logit Scaling:** A temperature-adjusted softmax is applied to these dot-product scores to create a probability distribution across all candidates.

### 4. Output Delivery
The final output is delivered to the user in a structured format based on the "
* **Noul:** Delivers a single probability (0 to 1) indicating how likely a statement is to be true.
* **Choice:** Delivers the most likely category (e.g., "billing") along with a ion and a confidence score.
* **Score:** Delivers an "expected level" (e.g., 1.98 on a scale of 0–2) based on a provided rubric.
* **Rank:** For free-form candidates like code snippets or tool-calls, the systdates **ordered by their alignment probability**, with the best match first.
